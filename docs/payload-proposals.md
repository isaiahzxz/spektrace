# Sandbox payload proposals: first slice

The local inspector can request a proposal, review a separate candidate, and explicitly replace the candidate editor with it. Existing Run Test and human acceptance remain separate. Passing the supported body check does not establish business correctness, explain the original HTTP response, or authorize replay.

This slice supports one canonical integer-string conversion at an evidence-supported object pointer. For example, synthetic `{"amount":"100"}` can become `{"amount":100}`. Decimal strings (`"12.5"`), nonnumeric strings, exponent/whitespace/leading-zero representations, unsafe integers, missing values, arrays along the pointer, prototype keys, redacted bodies, omitted data, unsupported checks, and already-passing checks require human input. No rounding, currency-unit conversion, field deletion, or business-value invention is allowed.

The model receives only bounded finding indices, conservative JSON pointers, and type labels. It selects an allowlisted transformation or abstains. Request bodies, numeric values, service metadata, repositories, and documentation are excluded. Replacement values and extra plan fields are rejected. The actual outbound request is scanned; the provider call has a 30-second timeout, bounded streamed response, one request and no retries. Secret scanning is heuristic, not a DLP guarantee.

Before model invocation, the service verifies workspace/service/environment/pinned revision scope, strict original evidence, a fresh body check, and stage-1 export completeness. It constructs a candidate locally, checks the full supported pinned schema, and compares the incident/specification fingerprint again before returning it. No original incident, validation evidence, approval, specification, or outbox record is modified by proposal generation. Candidates are returned for review, not persisted.

`SPEKTRACE_PAYLOAD_PROPOSALS_ENABLED` defaults off. The public server action is development-only, validates the incident ID, derives workspace from the local pilot configuration, and limits concurrent requests to two per server process. This is a local pilot control, not production authentication or distributed rate limiting. `SPEKTRACE_PAYLOAD_PROPOSAL_MODEL` defaults to `openai/gpt-4.1`; the existing server-only `THESYS_API_KEY` is required. The inspector shows unavailable status before clicking when the feature is off or unconfigured. Enabling the feature permits one paid request per explicit eligible click; model request-body values remain excluded.

The UI shows candidate JSON, transformation path, provider/model, source-body hash, pinned-spec reference/hash, and candidate hash. Applying explicitly replaces the editor and selects the pinned revision, clearing prior test results. It does not approve the incident. The inspector is keyed by incident, pending responses are discarded after unmount, and Run Test/Accept are disabled while preparing a proposal.

## Review UI safeguards

The sandbox now shows a line diff immediately above the candidate editor. Removed lines retain the stored original text, including quotes, and added lines show the current candidate text. The diff updates with manual edits. Unapplied proposal previews use the same comparison; after applying an identical proposal, the editor comparison supplies the diff without duplicating it in the preview. Comparison is text-based, so duplicate keys and incomplete JSON edits are not silently normalized away. Comparisons are bounded to 300 lines and 65,536 characters per side; larger comparisons explicitly show the complete stored original for review beside the existing candidate editor rather than hiding changes.

The eligibility section directly above Accept now says: “Passing schema check does not guarantee backend/business correctness. It does not explain the original HTTP failure.” The button describes itself with that paragraph via `aria-describedby`. Existing test and acceptance services are unchanged.
