# Structured source explanations

Live gateway requests with deployment context now use prompt `spektrace-investigation-explanation@39-source-facts-v2` and a strict version-2 response shape. Incident-only, repository-only, and documentation-only requests retain their existing response contracts, with prompt versions 36, 37, and 38 respectively. No database migration or inspector redesign is required.

The model returns separate `incidentFindings`, `repositoryObservations`, `documentationObservations`, and `deploymentFacts`. A deployment fact has only an exact supplied `recordId`, a recorded `status` or null, and a verified `commitRelationship` or null. There is no prose field. Both null is rejected. Duplicate records, unsupported statuses, unknown IDs, missing snapshot hashes, inconsistent comparison flags, and false SHA relationships are rejected.

`incidentFindings` selects supplied incident evidence IDs; it contains no model-written prose. SpekTrace renders the actual validation status, up to three stored findings per incident (noting omitted findings), and a separately recorded HTTP status with an explicit causation limit. It also generates the short incident summary and evidence limitations. Deployment status and commit comparison are rendered as separate sentences. Repository and documentation observations must identify their own supplied excerpt. `manualReviewChecks` selects closed codes for neutral manual evidence review; no arbitrary action text is accepted. The normalized result goes through the existing size, citation, claim, and unsafe-action guards, then is stored in the existing explanation shape for the inspector. The unnormalized model draft is not stored as accepted explanation data.

The production and recording gateways mark this contract themselves. The processor requires version 2 when that server-side marker is present; legacy-shaped model output is rejected rather than treated as a fallback. Previously stored explanations and deterministic test-adapter outputs remain compatible.

Optional hypotheses use separate incident, repository, and documentation reference arrays. Labels must explicitly signal uncertainty, and both label and description require the corresponding source references. Deployment claims remain excluded from hypotheses. Conservative source-word guards reject deployment commentary in repository/documentation observations and missing context. The model cannot provide its own summary, limitations, or suggested steps. Runtime-acceptance claims and known recommendations to relax validation are rejected. These checks can reject legitimate wording and do not prove the semantic correctness of arbitrary prose.

The two founder-reviewed mixed-source sentences are regression fixtures. Offline tests verify rejection of those sentences in deployment facts, source-specific citations, exact status/SHA checks, legacy fallback rejection, generated schema, both real gateway adapters with mocked HTTP, existing persistence rejection behavior, and output limits. Existing records are not rewritten.

The synthetic review tool can screen a single indexed prose field from a strictly parsed version-2 draft even when a scope guard rejects it. Schema failures and typed-field failures remain text-free. It never exposes raw draft JSON. Existing synthetic-only authorization, screening, one-use review capability, and five-minute expiry still apply.

During the authorized iterative synthetic checkpoint, eight one-request live runs were made without resets or queued inference retries. Seven used GPT-4.1-mini; one validator acceptance was rejected during primary-agent review because it inferred service acceptance and suggested relaxing validation. The final run used a process-only GPT-4.1 override and prompt 35, passed validation, and was considered acceptable in primary-agent review. It separated deterministic mismatch evidence from unexplained HTTP failure, cited source observations independently, labeled its serialization hypothesis uncertain, and suggested only manual evidence review. Founder review remains incomplete. This is one successful synthetic C sample, not proof of broad model reliability or a new A/B/C run on the final contract. Application AI and its model configuration were left unchanged. No support tickets, payload corrections, notifications, or production actions are introduced.

The founder subsequently approved that specific synthetic C example and requested explicit missing-runtime disclosures. The validator now adds absent request-correlated logs, absent traces, and unverified running version/validation configuration to every accepted explanation. It preserves additional model-provided missing context and exact-deduplicates disclosures, rejecting list/byte overflow rather than silently dropping entries.
